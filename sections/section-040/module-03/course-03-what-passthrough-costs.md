# Part 3 — What passthrough costs

> Prerequisite: [Part 2 — Configuring passthrough](./course-02-configuring-passthrough.md). Next: [the module landing page](./course.md), then [Section 050 — Authorization At The Edge](../../section-050/README.md).

The connection works. This part proves it worked the way the mode claims, lists exactly what stopped being available in exchange, and turns the choice between the three modes into one question.

## Proving the gateway did not terminate

A `200` looks identical in all three modes of this section. The distinguishing evidence is the certificate: in passthrough it belongs to the **backend**, because the backend is what completed the handshake.

> [!TIP]
> **Try it — read whose certificate answered**
>
> ```sh
> curl -sk -v --resolve secure.ica.local:8443:127.0.0.1 \
>   https://secure.ica.local:8443/ 2>&1 | grep -E 'subject:|issuer:|HTTP/'
> ```
>
> Expect something like:
>
> ```text
> * subject: CN=secure.ica.local; O=backend
> * issuer: CN=secure.ica.local; O=backend
> < HTTP/1.1 200 OK
> ```
>
> Compare that subject line with the one from [Part 1](./course-01-what-a-proxy-can-see.md), taken by port-forwarding directly to the backend with no gateway in the path. They are the same certificate — `O=backend`, generated by nginx at pod start. Nothing in between re-created or re-signed it, which is what "end to end" means in concrete terms.

The same conclusion is visible from the gateway's side, and it is visible as an **absence**. A terminated listener produces HTTP routes for its hostname; a passthrough listener produces an SNI-matching TCP filter chain and no HTTP routes at all.

> [!TIP]
> **Try it — look for HTTP routes that are not there**
>
> ```sh
> istioctl proxy-config listener deploy/istio-ingressgateway -n istio-system --port 443 -o json \
>   | grep -i -E 'tls_inspector|sniDomains|serverNames' | head
> istioctl proxy-config routes deploy/istio-ingressgateway -n istio-system | grep secure.ica.local \
>   || echo "no HTTP route for secure.ica.local — expected in passthrough"
> ```
>
> Expect something like:
>
> ```text
>                 "name": "envoy.filters.listener.tls_inspector",
>                     "serverNames": ["secure.ica.local"]
> no HTTP route for secure.ica.local — expected in passthrough
> ```
>
> `tls_inspector` is the listener filter from [Part 1](./course-01-what-a-proxy-can-see.md) — the thing that peeks at the ClientHello to read SNI without decrypting — and `serverNames` is your `sniHosts` compiled into a filter-chain match. The missing HTTP route is not a fault to fix; it is the mode working. Treat "no route" as confirmation here, and as a problem only in the terminating modes.

Two commands, two kinds of evidence, and together they rule out the alternative explanations: the certificate says the backend terminated, and the absent routes say the gateway never tried to.

## The complete list of what is gone

For passthrough traffic the gateway cannot:

- route on `uri`, `headers`, `method` or `queryParams`;
- rewrite a path, a host, or anything else;
- add, read or remove headers — including tracing headers, so a distributed trace breaks at this hop;
- produce L7 telemetry: no `istio_requests_total`, no response codes, no per-path latency. Only TCP-level metrics (`istio_tcp_connections_opened_total`, bytes) exist;
- apply retries, timeouts, fault injection, or any `VirtualService` `http` feature;
- apply any `AuthorizationPolicy` rule that mentions `methods`, `paths` or `hosts`.

Connection-level rules survive, because they never needed the payload: `ipBlocks`, `remoteIpBlocks`, destination `ports`. That is exactly the set [section 050](../../section-050/README.md) works with, and — not coincidentally — the same L4-only set ztunnel is limited to in [section 060](../../section-060/README.md). Three different reasons to be unable to read a request, one identical consequence.

In exchange, three things you cannot otherwise have:

- the client and the backend share a TLS session that nothing in between can read;
- the backend presents its own identity, which is what a caller pinning a certificate expects;
- a backend that authenticates callers by client certificate receives the **real** certificate, rather than a header summary from a gateway that terminated.

Because passthrough removes capabilities rather than adding them, its mistakes are mostly attempts to use features that no longer exist for this traffic.

> [!WARNING]
## Common pitfalls

> [!WARNING]
> **An `http` block in the `VirtualService`** — it cannot match an encrypted stream. The config applies cleanly and every connection fails, which makes this the module's signature mistake.
>
> **`protocol: HTTPS` with `mode: PASSTHROUGH`** — the protocol says "terminate and parse HTTP" while the mode says "do not decrypt". Use `protocol: TLS`.
>
> **`hosts` and `sniHosts` naming different hostnames** — both match the same SNI value, so a mismatch routes nothing.
>
> **Connecting by IP, or otherwise without SNI** — the routing rule has no input. Always test with `--resolve` or real DNS.
>
> **Expecting path-based routing, header rules or L7 metrics** — none of it exists for this traffic. If a requirement needs them, passthrough is the wrong mode.
>
> **Expecting a `404` or `403` when something is misconfigured** — producing either would require reading the request. Misrouted passthrough fails as a connection error.
>
> **Routing to the backend's plaintext port** — the destination must be the port where the backend terminates TLS itself.
>
> **Assuming tracing still works across the hop** — the gateway cannot add or propagate headers it cannot see.

## Choosing a mode

The decision reduces to one question: **does the backend need to see the original TLS session?**

```text
   does the backend need the original TLS session?
        │
       yes ──▶  PASSTHROUGH
        │       (it presents its own certificate, or it authenticates
        │        callers by their client certificate, or a policy forbids
        │        any intermediary from decrypting)
        │
       no  ──▶  terminate at the gateway
                    │
                    ├── clients are the public          ──▶  SIMPLE
                    └── clients are a known, short list ──▶  MUTUAL
```

Terminating is the better default when nothing forces otherwise: it gives routing, observability, retries, and one place to manage certificates. Passthrough is a deliberate trade of all of that for end-to-end secrecy.

Serving both from one gateway is normal and expected — different hostnames on different `servers` entries, each in whichever mode its backend needs, selected by SNI at connection time. The modes are per listener, not per gateway, so the choice is made once per hostname rather than once per cluster.

One related mode worth recognising by name: **`AUTO_PASSTHROUGH`**, which routes by SNI without requiring a matching `VirtualService`. It exists for multicluster gateways, where the SNI encodes the destination service, and it is not something to reach for in ordinary ingress.

> *Passthrough trades every L7 capability for a session no intermediary can read — and the certificate the client receives is the proof of which side of that trade you are on.*
